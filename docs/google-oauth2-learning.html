02 · THE SECURITY IDEA

Authenticate, identify, authorize

01

Authenticate · Google

Google proves that the person controls a Google identity. Spring's OIDC support validates the response.

02

Identify · Our database

The app resolves the validated (issuer, subject) pair to a local user. Email alone does not silently link accounts.

03

Authorize · Our app

Our database roles decide access. A new Google sign-in receives ROLE_CUSTOMER, never admin by identity alone.

Important project detail: Google sign-in is on the customer storefront at localhost:5174. The admin login at localhost:5173 is email/password.

05 · INTERVIEW PRACTICE

Ask yourself “why?”

Try answering aloud before opening each suggested answer.

Is Google sign-in OAuth 2.0 or OpenID Connect?

Both: it uses the OAuth 2.0 Authorization Code flow with OIDC for standardized user authentication and an ID token.

Why not use the email address as the provider identity key?

Email can change and is profile data. A validated issuer and subject pair identifies the external account; local roles remain controlled by our app.

Why exchange the authorization code on the backend?

This confidential client can protect its client secret, validate the provider response, apply account policy, and issue an app-specific credential without exposing secrets to JavaScript.

What do state, nonce, and CSRF each protect?

State correlates the OAuth request and callback. OIDC nonce binds the ID token to its authentication request. The CSRF token protects the later cookie-backed exchange POST. They are related security controls, not interchangeable values.

Why issue an application JWT instead of using Google's token?

Our APIs need our own issuer, audience, local user ID, roles, and expiry. Google tokens are for the Google client or Google APIs, not generic credentials for this application.

Why keep a temporary session if APIs use JWT?

The redirect flow needs short-lived state across browser round trips. The OAuth session is consumed during the exchange; ordinary API requests use stateless application JWTs.

What happens if a user already has a password account with the same email?

This project denies an automatic link. The user should sign in to the existing account and complete a deliberate verified account-linking flow if linking is supported.

YOUR 30-SECOND ANSWER

“Google authenticates the customer using OIDC. Our backend validates the provider response, resolves a local account by issuer and subject, and checks the local customer role. It then exchanges a short-lived, CSRF-protected OAuth session for our own JWT. Our APIs trust that JWT—not Google's token.”
